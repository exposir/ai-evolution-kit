## 3 分钟电梯演讲脚本

### [0-30s] 问题背景 - 为什么做这个项目？

**话术**：
"在学习 AI 开发过程中，我发现市面上教程存在两个极端：

1. **只教调 API** - 停留在 `openai.chat.completions.create()` 层面，遇到问题不知道从哪调试
2. **直接用框架全家桶** - 上来就 LangChain、LlamaIndex，出问题只能盲目搜索 Issue

这导致很多开发者不理解 Agent 的本质原理，成为'调包侠'。

**我的解决方案**：从裸金属开始，先手写核心算法（ReAct 循环、余弦相似度），理解原理后再逐步引入框架（LangGraph、Vercel AI SDK），构建生产级应用。"

---

### [30s-1min30s] 解决方案 - 我做了什么？

**话术**：
"项目分 5 个 Milestone，22 个章节，渐进式学习：

**M1: Runtime Lab (Ch1-8)** - AI 运行时基础
- 手写 ReAct 循环：理解 `Tool Calling → 执行 → 结果回传` 的闭环
- 手写余弦相似度：理解向量检索的数学原理
- 实现 MCP 协议：理解工具声明与调用的解耦

**M2: Data Forge (Ch9-11)** - 解决'脏数据'和'失忆'问题
- 递归文本切分：保持语义完整性，而非暴力按字符数切
- Supabase + pgvector：构建生产级向量数据库
- 混合检索：Vector Search (语义) + Keyword Search (精确匹配)

**M3: Agent Brain (Ch12-15)** - 从命令式到声明式
- StateGraph：用图结构描述 Agent 流程，替代嵌套 if/else
- 自我修复回路：Conditional Edge 实现失败重试
- Supervisor 模式：一个协调者 + 多个专家 Agent 协作

**M4: Next Client (Ch16-19)** - 丝滑的 AI 交互体验
- 流式 UI：让用户实时看到 AI 思考过程
- 生成式 UI：AI 返回结构化数据 → 前端渲染组件（v0.dev 原理）
- streamObject：边生成边解析 JSON

**M5: Server Core (Ch20-22)** - 生产级后端
- NestJS 模块化：Controller/Service/Guard 分层
- Redis 会话管理：24 小时 TTL 自动过期
- 三级限流：1s/10s/60s 分层防护，控制 API 成本"

---

### [1min30s-3min] 技术亮点 - 我的核心竞争力

**话术**：
"核心亮点有三个维度：

**1. 手写核心算法 - 证明技术深度**
- **余弦相似度**：能白板复现，理解向量检索原理
  ```typescript
  dotProduct / (normA * normB)  // 关注方向，不受模长影响
  ```
- **ReAct 循环**：理解状态机转换，知道为什么需要 `tool_call_id` 回传
- **递归文本切分**：策略模式（段落 → 句子 → 字符），保证语义完整

**2. 架构演进 - 展示系统性思维**
```
M1: while (response.tool_calls) { if/else }
    ↓ 问题：复杂流程难维护，重试逻辑硬编码
M3: StateGraph + ConditionalEdges
    ↓ 优势：声明式描述流程，图结构支持复杂路由
M5: NestJS + Redis + 三级限流
    ↓ 生产：模块化 + 持久化 + 成本控制
```

**3. 生产级特性 - 证明落地能力**
- **三级限流**：1s 10 次（防暴力）/ 10s 100 次（防爬虫）/ 60s 1000 次（防滥用）
- **POST 缓存**：基于请求体 Hash，命中率 30% 时节省 30% 成本
- **会话 TTL**：Redis 24 小时自动过期，避免冷数据占用内存
- **AI SDK 兼容性**：v4 的 `compatibility: 'compatible'` 支持智谱 AI"

### [3min+] 追问应对准备

#### Q: 为什么选择手写而不是直接用框架？

**A**: "先理解原理，遇到问题才知道从哪调试。

比如向量检索不准，如果不懂余弦相似度，就无法判断是：
- Embedding 模型问题（向量质量差）
- 检索策略问题（k 值太小）
- 切分问题（破坏了语义）

手写过一遍后，用框架时能快速定位根因，而不是盲目调参数。"

---

#### Q: 项目中遇到的最大技术难点是什么？

**A**: "架构演进过程中的权衡。

**具体案例 - 自我修复回路**：
- M1 手工实现需要 30 行嵌套 if/else，逻辑清晰但扩展性差
- M3 用 LangGraph 只需 5 行声明 ConditionalEdge，但要重新理解声明式编程

**关键决策**：
- 简单场景（3 个节点以内）用 while 循环，直观易调试
- 复杂场景（多分支、循环、中断）用 LangGraph，架构清晰

这让我深刻理解了'好的架构能让复杂性消失'。"

---

#### Q: 如何验证学习效果？

**A**: "三个层次的验证：

**代码层**：
- M1-M5 每个包都有可运行的 demo
- M6 全栈验证，前端 + 后端 + 数据库完整联调

**问题层**：
- 能回答'为什么'：为什么用余弦而非欧氏距离？
- 能解决'怎么办'：检索不准怎么排查？

**实战层**：
- 会话持久化解决了重启丢失上下文的实际问题
- 三级限流控制了 API 成本（每次对话 < $0.01）

最重要的验证：现在可以全栈交付 AI 产品，不依赖后端同学。"

## 技术栈详细清单

### AI 层
- **LLM Provider**: OpenAI GPT-4, GPT-3.5, DeepSeek
- **Embedding**: OpenAI text-embedding-3-small (1536 维), 智谱 embedding-3 (2048 维)
- **工具调用**: Tool Calling (Function Calling), MCP Protocol

### 编排层
- **LangGraph**: StateGraph, Annotation, Conditional Edge, Interrupt
- **LangChain**: ChatOpenAI, AIMessage, ToolMessage

### 前端层
- **框架**: Next.js 15 (App Router), React 19
- **AI SDK**: Vercel AI SDK v4 (useChat, streamText, streamObject, streamUI)
- **样式**: Tailwind CSS 4, shadcn/ui
- **状态管理**: React Hooks (useState, useReducer)

### 后端层
- **框架**: NestJS 11
- **DI**: @Module, @Injectable, @Controller
- **中间件**: Guard (Auth, Throttle), Interceptor (Cache)
- **验证**: class-validator, class-transformer

### 数据层
- **向量数据库**: Supabase (PostgreSQL + pgvector)
- **缓存**: Redis (Upstash), ioredis
- **ORM**: Supabase SDK

### 开发工具
- **包管理**: pnpm workspace (Monorepo)
- **语言**: TypeScript 5.x
- **类型校验**: Zod
- **代码质量**: ESLint, Prettier

## 对标分析

### vs 市面上 AI 教程

| 维度 | 市面上教程 | 本项目 |
|------|------------|--------|
| **学习路径** | 碎片化 | 22 章节渐进式 |
| **原理理解** | 直接用框架 | 先手写再用框架 |
| **代码质量** | Demo 级别 | 生产级代码 |
| **技术栈** | 单一（纯前端或纯后端）| 全栈（前端 + 后端 + 数据）|
| **实战验证** | 无 | M6 完整验证 |

### vs 纯前端项目

| 维度 | 纯前端项目 | 本项目 |
|------|------------|--------|
| **AI 原理** | 黑盒调 API | 手写核心算法 |
| **后端能力** | 依赖后端同学 | NestJS 全栈交付 |
| **数据处理** | 不涉及 | Redis + pgvector |
| **系统设计** | 不涉及 | 限流、认证、缓存 |

### vs 纯后端项目

| 维度 | 纯后端项目 | 本项目 |
|------|------------|--------|
| **用户体验** | 关注性能指标 | 流式 UI + 组件化 |
| **状态管理** | 关注数据库状态 | 前端状态 + 后端持久化 |
| **交互细节** | 不关注 | SSE、Skeleton、Loading |
