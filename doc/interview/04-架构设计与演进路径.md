# 架构设计与演进路径

> 展示系统性思维

## 一、整体架构演进路径

### Phase 1: 裸金属理解原理（M1）

```
┌─────────────────────────────────────┐
│         Node.js Process              │
│  ┌──────────────────────────────┐   │
│  │   While Loop (Ch3)           │   │
│  │   - OpenAI API               │   │
│  │   - Tool Calling             │   │
│  │   - Message 数组维护上下文    │   │
│  └──────────────────────────────┘   │
└─────────────────────────────────────┘
```

**设计目标**: 理解 Agent 闭环本质  
**核心决策**: 不用框架，手写核心逻辑

│  └──────────┬───────────────────┘   │
└────────────┼────────────────────────┘
             │

│  ┌──────────────────────────────┐   │
│  │   documents 表               │   │
│  │   - content TEXT             │   │

│  │   - metadata JSONB           │   │

## 二、关键技术选型理由

### 1. 为什么选 LangGraph 而非 LangChain？

| LangChain | LangGraph |
|-----------|-----------|
| 链式调用，顺序执行 | 图结构，支持条件分支 |
| 适合简单流程 | 适合复杂编排 |
| 调试困难（黑盒） | 状态透明，易调试 |

**实际案例**: Ch13 自我修复回路需要 Conditional Edge，LangChain 无法实现。

---

### 2. 为什么选 Vercel AI SDK 而非自己封装？

**对比方案**:
- 方案 A: 自己封装 OpenAI SDK  
  问题: SSE 流式传输、错误处理、类型定义都要自己做
  
- 方案 B: Vercel AI SDK  
  优势: useChat 自动管理状态、streamObject 解析结构化输出、工具调用自动路由

**决策**: 专业的事交给专业工具，节省 80% 重复劳动

---

### 3. 为什么选 Supabase 而非 Pinecone？

| Pinecone | Supabase |
|----------|----------|
| 专业向量库 | PostgreSQL + pgvector |
| 按使用量计费 | 免费额度慷慨 |
| 黑盒 | SQL 可见，学习价值高 |

**决策**: 学习项目优先选透明方案，生产项目再考虑专业工具

## 三、架构决策记录（ADR）

### ADR-001: 使用 pnpm monorepo 管理 6 个 Package

**背景**: 22 章内容需要清晰的模块划分  
**决策**: Monorepo 而非 Multi-repo  
**理由**:
- 共享 tsconfig、.env、依赖版本
- 本地开发无需 npm link
- 统一的测试和构建流程

---

### ADR-002: AI SDK 4 而非 AI SDK 5/6

**背景**: AI SDK 5/6 使用新的 /responses API  
**决策**: 锁定 v4  
**理由**:
- 使用 OpenAI 兼容 API
- v4 的 `compatibility: 'compatible'` 模式支持智谱 AI
- v5/6 的 /responses 端点兼容性差

---

### ADR-003: Redis 会话 TTL 设置为 24 小时

**背景**: 会话数据需要自动清理  
**决策**: 24 小时 TTL  
**理由**:
- 覆盖单日工作场景
- 避免冷数据占用内存
- 超过 24 小时的对话可认为是新会话

## 四、演进过程中的权衡

### 权衡 1: 简单性 vs 可扩展性

**场景**: ReAct 循环实现

**方案 A - While 循环**:
- 优势: 简单直观，易调试
- 劣势: 复杂逻辑难维护

**方案 B - LangGraph**:
- 优势: 声明式，易扩展
- 劣势: 学习曲线，调试需理解图执行流程

**最终选择**: 两者都实现
- M1 用 while 理解原理
- M3 用 LangGraph 重构
- 根据场景选择：简单用 while，复杂用 LangGraph

---

### 权衡 2: 性能 vs 成本

**场景**: 向量数据库索引

**方案 A - 创建索引**:
- 优势: 查询快
- 劣势: pgvector 限制 2000 维，智谱 embedding-3 是 2048 维

**方案 B - 无索引**:
- 优势: 无维度限制
- 劣势: 查询慢（但数据量小时可接受）

**最终选择**: 无索引
- 学习项目数据量小（< 1000 条）
- 性能差异可忽略（< 100ms）
- 避免被限制束缚

---

### 权衡 3: 自建 vs 托管

**场景**: Redis 部署

**方案 A - 本地 Docker**:
- 优势: 完全控制
- 劣势: 运维成本

**方案 B - Upstash（托管）**:
- 优势: 免运维，免费额度充足
- 劣势: 依赖外部服务

**最终选择**: Upstash
- 学习项目无需考虑运维
- 免费额度覆盖开发测试
- 生产可无缝迁移到自建

## 五、面试话术

### Q: 你的架构是如何演进的？

**A**: "架构演进遵循'理解原理 → 引入框架 → 生产优化'的路径：

**M1 阶段**：手写 while 循环理解 ReAct 本质，代码 50 行，逻辑清晰但扩展性差。

**M3 阶段**：用 LangGraph 重构，声明式图结构支持复杂流程，代码降到 30 行，架构清晰。

**M5 阶段**：加入生产级特性（限流、认证、缓存），用 NestJS 模块化管理，支持横向扩展。

这个过程让我深刻理解了'好的架构能让复杂性消失'。"

---

### Q: 为什么选择 Monorepo？

**A**: "22 章内容分 6 个 Milestone，Monorepo 带来三个关键优势：

1. **依赖统一**：共享 TypeScript 配置、ESLint 规则，避免版本冲突
2. **开发效率**：无需 npm link，本地引用即可，热更新快
3. **原子提交**：跨包修改一次提交，保证一致性

相比 Multi-repo，虽然灵活性稍差，但学习项目更重视开发体验。"
