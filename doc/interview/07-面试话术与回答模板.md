## 二、技术深度类

### Q3: 解释一下 ReAct 循环的原理

**标准答案**:

"ReAct 是 Reason + Act 的缩写，核心是'模型思考 → 调用工具 → 结果回传 → 继续思考'的闭环。

**具体实现分三步**：
1. 发送 messages + tools 给 LLM
2. 如果返回 tool_calls，执行工具并构造 role: 'tool' 消息
3. 将结果追加到 messages 数组，继续循环，直到没有 tool_calls

**关键点**：
- 循环终止条件是 response.tool_calls 为空
- 每次调用都要携带完整的 messages 数组（上下文）
- 工具结果必须用 role: 'tool' 标记，否则模型无法理解"

**代码演示**:

```typescript
while (true) {
  const response = await openai.chat.completions.create({ messages, tools });
  if (!response.tool_calls) break;
  
  for (const call of response.tool_calls) {
    const result = runTool(call.function.name, call.function.arguments);
    messages.push({ role: 'tool', tool_call_id: call.id, content: result });
  }
}
```

### Q4: RAG 的核心原理是什么？如何优化检索质量？

**标准答案**:

"RAG（检索增强生成）核心是'检索相关知识 → 注入 Prompt → LLM 回答'。

**核心流程**:
1. 离线: 文档切分 → Embedding → 存向量库
2. 在线: 用户提问 → Embedding → 检索 Top-K → 构造 Context → LLM 生成

**优化策略**:
1. **切分质量**: 用递归切分保持语义完整性
2. **Embedding 模型**: OpenAI text-embedding-3 比 ada-002 好
3. **混合检索**: Vector Search（语义）+ Keyword Search（精确匹配）
4. **Chunk Overlap**: 保证跨块语义连续
5. **Metadata 过滤**: 按文档类型、时间范围缩小检索范围"

**追问准备**:

**Q**: 为什么用余弦相似度而不是欧氏距离？  
**A**: "余弦关注方向，欧氏关注距离。文本 Embedding 是高维空间的方向向量，更关心语义方向而非绝对值。"

### Q5: LangGraph 和 LangChain 的区别？

**标准答案**:

| 维度 | LangChain | LangGraph |
|------|-----------|-----------|
| 流程控制 | 链式调用 | 图结构 |
| 分支支持 | 差 | 好（Conditional Edge）|
| 状态管理 | 隐式 | 显式（Annotation）|
| 调试难度 | 高（黑盒）| 中（状态可见）|
| 适用场景 | 简单流程 | 复杂编排 |

**实际案例**:
"LangChain 适合线性流程，比如'检索 → 生成'。但如果需要自我修复回路（生成 → 验证 → 失败则重试 → 超过 3 次则放弃），LangChain 很难实现，而 LangGraph 用 ConditionalEdge 很自然。"

## 三、系统设计类

### Q6: 如果让你设计一个生产级的 RAG 系统，你会怎么做？

**STAR 回答**:

**S**: "假设要为企业内部文档构建 RAG 系统，日活 1000 人，文档库 10GB。"

**T**: "需要解决检索质量、响应延迟、成本控制三个核心问题。"

**A**: "我会设计分层架构：

**数据层**:
- Supabase + pgvector 存储向量
- Redis 缓存热点 Embedding
- Metadata 字段存储文档类型、部门、时间

**检索层**:
- 混合检索：Vector Search + Keyword Search
- Rerank 模块二次排序
- Query 改写提升召回

**生成层**:
- Prompt Template 标准化
- 流式输出降低感知延迟
- Response 缓存节省成本

**监控层**:
- LangSmith 追踪每次调用
- 成本监控（Token 消耗）
- 用户反馈（点赞/点踩）"

**R**: "关键指标：Recall@5 > 90%，P99 延迟 < 3s，单次查询成本 < $0.01。"

### Q7: 如何处理高并发场景？

**标准答案**:

"高并发场景下的核心问题是 LLM API 调用慢（1-3s），用户不能等太久。

**解决方案**:

**前端优化**:
- 流式 UI，让用户看到渐进结果
- Skeleton 占位，降低焦虑感

**后端优化**:
- Redis 缓存常见问题
- 批量 Embedding（减少 API 调用）
- 连接池复用（数据库、Redis）

**架构优化**:
- 消息队列（Kafka）异步处理
- 多副本部署 + 负载均衡
- CDN 缓存静态资源

**限流策略**:
```typescript
@Throttle({ 
  short: { limit: 10, ttl: 1000 },   // 1s 10次（防暴力）
  medium: { limit: 100, ttl: 10000 }, // 10s 100次（防爬虫）
  long: { limit: 1000, ttl: 60000 }   // 1min 1000次（防滥用）
})
```"

## 四、场景题

### Q8: 用户反馈"AI 回答不准"，你怎么排查？

**STAR 回答**:

**S**: "用户反馈 AI 对技术文档的回答经常答非所问。"

**T**: "需要快速定位是检索问题还是生成问题。"

**A**: "我采用分层排查：

**Step 1: 检索诊断**
```typescript
const docs = await vectorSearch(query, k=10);
console.log('Retrieved docs:', docs.map(d => ({
  content: d.content.slice(0, 100),
  similarity: d.similarity
})));
```
发现 Top-1 相似度 < 0.7，说明检索质量差。

**Step 2: 根因分析**
- 固定长度切分破坏了代码块语义
- 纯向量检索对函数名不敏感

**Step 3: 改进方案**
1. 递归切分保持语义完整
2. 混合检索：向量 0.7 + 关键词 0.3
3. 加入 Rerank 二次排序"

**R**: "Recall@5 从 60% 提升到 90%，用户满意度显著提高。我理解了 RAG 的核心不是模型，而是检索质量。"

## 五、软技能类

### Q10: 你在项目中遇到过最大的挑战是什么？

**STAR 回答**:

**S**: "在 M5 实现会话持久化时，用户反馈重启后对话历史丢失。"

**T**: "需要在不影响性能的前提下，实现会话状态的持久化。"

**A**: "我研究了三种方案：
1. LocalStorage（前端）- 问题：跨设备不同步
2. 数据库（PostgreSQL）- 问题：每次请求都查询，延迟高
3. Redis - 优势：内存速度快 + TTL 自动过期

选择 Redis 后，设计了完整的生命周期：
- 前端生成 sessionId（支持匿名用户）
- 后端每次对话后 `setex(sessionId, 86400, state)`
- 24 小时 TTL 自动清理冷数据"

**R**: "最终 P99 延迟 < 50ms，内存占用可控。这个经验让我理解了'架构设计就是权衡的艺术'。"

### Q11: 你如何平衡学习新技术和完成项目？

**回答**:

"我采用'理论-实践-反思'循环：

**理论**: 先快速过一遍官方文档（1-2 小时）
**实践**: 立即写 demo 验证理解（避免眼高手低）
**反思**: 记录踩坑经验，更新文档

**具体案例 - 学习 LangGraph**:
1. 看官方文档理解 StateGraph 概念（1 小时）
2. 写 Ch12 demo 实现基础流程（2 小时）
3. 踩坑：不理解 Reducer 的作用，花 30 分钟调试
4. 记录到项目文档，下次直接查阅

这样既保证学习效率，又能快速迭代项目。"
