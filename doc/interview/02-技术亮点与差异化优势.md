## 一、手写核心算法（证明技术深度）

### 1. 余弦相似度 (Ch8)

#### 为什么手写？

向量检索是 RAG 的核心，必须理解数学原理。遇到精度问题、性能问题时能定位根因。

#### 代码实现

```typescript
function cosineSimilarity(vecA: number[], vecB: number[]): number {
  let dotProduct = 0;
  let normA = 0;
  let normB = 0;

  for (let i = 0; i < vecA.length; i++) {
    dotProduct += vecA[i] * vecB[i];
    normA += vecA[i] * vecA[i];
    normB += vecB[i] * vecB[i];
  }

  return dotProduct / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

**时间复杂度**: O(n)，n 是向量维度  
**空间复杂度**: O(1)

#### 面试追问准备

**Q**: 为什么用余弦相似度而不是欧氏距离？  
**A**: 余弦关注方向，欧氏关注距离。文本 Embedding 更关心语义方向而非绝对值。欧氏距离会被向量模长影响，不适合文本场景。

**Q**: 如何优化性能？  
**A**:
1. SIMD 指令并行计算（向量化）
2. 稀疏向量优化（跳过 0 值）
3. 批量计算时复用 normA

### 3. 递归文本切分 (Ch9)

#### 问题

固定长度切分会破坏语义。

#### 方案

按 段落 → 句子 → 字符 递归切分。

#### 代码实现

```typescript
class RecursiveTextSplitter {
  private separators = ['\n\n', '\n', '. ', ' '];
  
  split(text: string): string[] {
    return this.recursiveSplit(text, 0);
  }

  private recursiveSplit(text: string, level: number): string[] {
    if (text.length <= this.chunkSize) {
      return [text];
    }

    const sep = this.separators[level];
    const parts = text.split(sep);
    const chunks: string[] = [];
    let current = '';

    for (const part of parts) {
      if ((current + part).length > this.chunkSize) {
        if (current) chunks.push(current);
        current = part;
      } else {
        current += (current ? sep : '') + part;
      }
    }

    if (current) chunks.push(current);

    // 递归处理超长块
    return chunks.flatMap(chunk =>
      chunk.length > this.chunkSize && level < this.separators.length - 1
        ? this.recursiveSplit(chunk, level + 1)
        : [chunk]
    );
  }
}
```

#### 设计亮点

- 优先保持段落完整性
- 超长段落才降级到句子级别
- ChunkOverlap 保证跨块语义连续

## 二、架构演进（证明系统性思维）

### 从命令式到声明式的跃迁

```
M1: while (response.tool_calls) { if/else }
    ↓ 问题: 复杂流程难维护，重试逻辑硬编码
M3: StateGraph + ConditionalEdges
    ↓ 优势: 声明式描述流程，图结构支持复杂路由
```

### 具体案例 - 自我修复回路

#### M1 手工实现

```typescript
let retryCount = 0;
const maxRetries = 3;

while (true) {
  try {
    const result = await agent.run(input);
    if (validate(result)) {
      return result;
    } else if (retryCount < maxRetries) {
      retryCount++;
      input = fixInput(result);
      continue;
    } else {
      throw new Error('Max retries exceeded');
    }
  } catch (error) {
    if (retryCount < maxRetries) {
      retryCount++;
      continue;
    }
    throw error;
  }
}
```

需要 30 行 if/else，逻辑膨胀。

#### M3 LangGraph 实现

```typescript
const graph = new StateGraph(AgentState)
  .addNode('agent', agentNode)
  .addNode('validation', validationNode)
  .addConditionalEdges('validation', (state) => {
    if (state.errors && state.retryCount < 3) {
      return 'retry';
    }
    return state.errors ? 'fail' : 'success';
  })
  .addEdge('retry', 'agent')
  .compile();
```

只需 5 行声明 ConditionalEdge。

### 1. 三级限流策略 (Ch22)

#### 业务场景

API 成本高，需要防止滥用。

#### 实现方案

```typescript
@UseGuards(ThrottlerGuard)
@Throttle({
  short: { limit: 10, ttl: 1000 },   // 1s 10次 - 防暴力
  medium: { limit: 100, ttl: 10000 }, // 10s 100次 - 防爬虫
  long: { limit: 1000, ttl: 60000 },  // 60s 1000次 - 防滥用
})
export class ChatController {}
```

#### 设计思路

- **短期限流**: 防止暴力攻击
- **中期限流**: 防止爬虫持续请求
- **长期限流**: 防止账号滥用

#### 监控指标

- 429 错误率: 正常 < 1%，异常 > 10% 需调整
- P99 延迟: < 200ms（限流判断不应成为瓶颈）

#### 问题

相同问题重复调用 LLM 浪费成本。

#### 难点

POST 请求无法用 URL 做 Key。

#### 方案

请求体 Hash。

```typescript
private getCacheKey(dto: ChatRequestDto): string {
  return createHash('sha256')
    .update(JSON.stringify(dto.messages))
    .digest('hex');
}
```

#### 效果

命中率 30% 时可节省 30% API 成本。
