## 一、并发与性能

### 1. 三级限流策略 (Ch22)

#### 业务场景

防止 API 滥用，控制成本。

#### 实现方案

```typescript
@UseGuards(ThrottlerGuard)
@Throttle({ 
  short: { limit: 10, ttl: 1000 },   // 1s 10次 - 防暴力
  medium: { limit: 100, ttl: 10000 }, // 10s 100次 - 防爬虫
  long: { limit: 1000, ttl: 60000 }   // 60s 1000次 - 防滥用
})
export class ChatController {}
```

#### 设计思路

- **短期限流**: 防止暴力攻击（每秒超过 10 次立即拦截）
- **中期限流**: 防止爬虫持续请求
- **长期限流**: 防止账号滥用

#### 监控指标

- 429 错误率: 正常 < 1%，异常 > 10% 需调整策略
- P99 延迟: < 200ms（限流判断本身不应成为瓶颈）

### 2. POST 请求缓存 (Ch22)

#### 问题

相同问题重复调用 LLM 浪费成本。

#### 难点

POST 请求无法用 URL 做 Key。

#### 方案

请求体 Hash。

```typescript
@UseInterceptors(CacheInterceptor)
class ChatController {
  @Post('/chat')
  async chat(@Body() dto: ChatRequestDto) {
    const cacheKey = this.getCacheKey(dto);
    const cached = await this.redis.get(cacheKey);
    if (cached) return JSON.parse(cached);
    
    const result = await this.chatService.generateText(dto);
    await this.redis.setex(cacheKey, 300, JSON.stringify(result)); // 5min TTL
    return result;
  }
  
  private getCacheKey(dto: ChatRequestDto): string {
    return createHash('sha256')
      .update(JSON.stringify(dto.messages))
      .digest('hex');
  }
}
```

#### 效果

命中率 30% 时可节省 30% API 成本。

## 二、数据一致性与可靠性

### 1. 会话持久化 (Ch21)

#### 问题

用户刷新页面后对话历史丢失。

#### 方案

Redis Checkpointer。

```typescript
export interface ConversationState {
  sessionId: string;
  messages: Message[];
  metadata: Record<string, unknown>;
  createdAt: number;
  updatedAt: number;
}

class MemoryService {
  async saveConversation(sessionId: string, messages: Message[]) {
    const state: ConversationState = {
      sessionId,
      messages,
      metadata: {},
      createdAt: Date.now(),
      updatedAt: Date.now(),
    };
    await this.redis.setex(`conv:${sessionId}`, 86400, JSON.stringify(state));
  }
  
  async getConversation(sessionId: string): Promise<Message[]> {
    const data = await this.redis.get(`conv:${sessionId}`);
    return data ? JSON.parse(data).messages : [];
  }
}
```

#### 关键设计

- TTL 24 小时（避免冷数据占用内存）
- sessionId 由前端生成（支持匿名用户）
- metadata 预留扩展字段（如用户 ID、标签）

### 2. 向量入库批量处理 (Ch10)

#### 问题

逐条插入慢且容易失败。

#### 方案

批量插入 + 事务。

```typescript
async function batchInsert(chunks: DocumentChunk[]) {
  const batchSize = 100;
  
  for (let i = 0; i < chunks.length; i += batchSize) {
    const batch = chunks.slice(i, i + batchSize);
    
    const { error } = await supabase
      .from('documents')
      .insert(batch);
    
    if (error) {
      console.error(`Batch ${i}-${i + batchSize} failed:`, error);
      // 降级为逐条插入
      for (const chunk of batch) {
        await supabase.from('documents').insert([chunk]);
      }
    }
  }
}
```

#### 容错策略

- 批量失败后降级为逐条重试
- 记录失败的 chunk ID 供人工排查

## 三、安全与认证

### 1. API Key 认证 (Ch22)

```typescript
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const apiKey = request.headers['x-api-key'];
    
    if (!apiKey || apiKey !== process.env.API_KEY) {
      throw new UnauthorizedException('Invalid API Key');
    }
    
    return true;
  }
}

// 使用
@UseGuards(AuthGuard)
@Controller('chat')
export class ChatController {}
```

#### 安全增强

- 生产环境强制 HTTPS
- API Key 定期轮换
- 记录所有认证失败日志（审计 + 异常检测）

2. **中期（10s 100次）**: 防止爬虫持续请求
3. **长期（60s 1000次）**: 防止账号滥用，控制总体成本

用 NestJS 的 ThrottlerGuard 实现，配置三个时间窗口。监控 429 错误率，正常 < 1%。"

### Q: 如何保证会话状态的一致性？

**A**: "用 Redis 实现会话持久化：

**生命周期管理**:
- 前端生成 sessionId（UUID）
- 后端每次对话后 `setex(sessionId, 86400, state)`
- 24 小时 TTL 自动清理

**关键设计**:
- sessionId 由前端生成，支持匿名用户
- metadata 预留扩展字段
- P99 延迟 < 50ms，不影响性能

这个方案解决了重启丢失上下文的问题，同时控制了内存占用。"
